# Chapter 35 — Network Monitoring — Detailed Notes

## 1. What Is Network Monitoring?

Network monitoring is the continuous process of observing network infrastructure, traffic, systems, services, and applications.

The purpose is to understand:

* Availability
* Performance
* Reliability
* Capacity
* Security
* Errors
* Failures

A DevOps Engineer uses monitoring to detect problems before they become major incidents.

Example:

```text
Users
  |
  v
Load Balancer
  |
  v
Application
  |
  v
Database
```

We can monitor every layer.

---

# 2. Why Network Monitoring Matters

Without monitoring, you may only discover a problem when users report it.

With monitoring:

```text
Problem
   ↓
Metric changes
   ↓
Alert
   ↓
Investigation
   ↓
Fix
   ↓
Verification
```

Network monitoring helps with:

* Early detection
* Faster troubleshooting
* Performance analysis
* Capacity planning
* Security investigation
* Availability tracking
* Incident response

---

# 3. Monitoring vs Observability

These concepts are related but not identical.

### Monitoring

Monitoring tells us whether known conditions are healthy.

Example:

```text
CPU > 80%
Latency > 500 ms
Packet loss > 5%
```

### Observability

Observability helps us understand **why** something is happening by examining system outputs such as:

* Metrics
* Logs
* Traces
* Events

Simple mental model:

```text
Monitoring → Is something wrong?

Observability → Why is it wrong?
```

---


```text
Network
   ↓
```

# 5. Metrics

Metrics are numerical measurements collected over time.

Examples:

```text
CPU Usage = 70%
Memory Usage = 65%
Latency = 120 ms
Packet Loss = 1%
Network Traffic = 500 Mbps
```

Metrics are useful for:

* Dashboards
* Alerting
* Capacity planning
* Trend analysis

---

# 6. Logs

Logs are records of events generated by systems.

Example:

```text
2026-09-10 20:10:01 connection refused
2026-09-10 20:10:05 DNS lookup failed
```

Logs provide detailed information about what happened.

Examples:

* Application logs
* System logs
* Firewall logs
* Authentication logs
* Kubernetes logs

---

# 7. Events

An event represents something that happened.

Examples:

```text
Server restarted
Pod deleted
Network interface changed
Security rule modified
```

Events are useful for understanding changes in infrastructure.

---

# 8. Traces

A trace follows a request through multiple services.

Example:

```text
User
 ↓
API Gateway
 ↓
Service A
 ↓
Service B
 ↓
Database
```

A trace can show where a request spent most of its time.

This is especially useful in microservices.

---

# 9. Availability

Availability describes whether a service is reachable and functioning.

Example:

```text
Service available → UP
Service unavailable → DOWN
```

A monitoring system may periodically check:

```text
Is the server reachable?
Is the port open?
Is the application responding?
```

---

# 10. Uptime

Uptime is the amount of time a service remains operational.

Example:

```text
Total time = 30 days
Downtime = 10 minutes
```

The goal of production systems is usually high availability.

---

# 11. Latency

Latency is the time required for data or a request to travel between systems.

Example:

```text
Client
  |
  | Request
  ↓
Server
  |
  | Response
  ↓
Client
```

If the round-trip time is 20 ms, the network response is relatively fast.

If it becomes 500 ms, users may notice slow applications.

Common latency sources:

* Network congestion
* Long network path
* DNS resolution
* Server processing
* Database queries
* Cloud routing

---

# 12. Packet Loss

Packet loss happens when packets do not successfully reach their destination.

Example:

```text
100 packets sent
5 packets lost
```

Packet loss:

```text
5%
```

Packet loss can cause:

* Retransmissions
* Slow TCP connections
* Application failures
* Poor voice/video quality

---

# 13. Jitter

Jitter is the variation in packet delay.

Example:

```text
Packet 1 → 20 ms
Packet 2 → 22 ms
Packet 3 → 25 ms
Packet 4 → 90 ms
```

The large variation indicates jitter.

Jitter is especially important for:

* Voice calls
* Video conferencing
* Gaming
* Real-time applications

---

# 14. Bandwidth

Bandwidth represents the maximum capacity of a network link.

Example:

```text
Network link = 1 Gbps
```

This means the link has a theoretical capacity of 1 Gbps.

Bandwidth is not the same as actual data transfer.

---

# 15. Throughput

Throughput is the actual amount of data transferred successfully over the network.

Example:

```text
Bandwidth = 1 Gbps
Actual throughput = 700 Mbps
```

Therefore:

```text
Bandwidth → Capacity

Throughput → Actual transfer
```

---

# 16. Errors and Drops

Network interfaces may report:

* Receive errors
* Transmit errors
* Dropped packets
* Collisions
* Carrier errors

Check interface statistics with:

```bash
ip -s link
```

A sudden increase in errors or drops can indicate a network problem.

---

# 17. Connections

Network monitoring should track active connections.

Useful command:

```bash
ss -s
```

For detailed connections:

```bash
ss -ant
```

Listening ports:

```bash
ss -lntp
```

A sudden increase in connections may indicate:

* Increased traffic
* Application problems
* Connection leaks
* Misconfiguration
* Possible attack

---

# 18. Network Saturation

Saturation occurs when a resource approaches or reaches its capacity.

Example:

```text
Network utilization

40%
50%
60%
70%
80%
90%
100%
```

At high utilization, performance may degrade.

Monitor saturation before it becomes an outage.

---

# 19. Network Baseline

A baseline describes normal system behavior.

Example:

```text
Normal latency: 20–50 ms
Normal packet loss: <1%
Normal traffic: 100–300 Mbps
Normal connections: 500–1000
```

Once the baseline is known, unusual behavior becomes easier to identify.

---

# 20. Active Monitoring

Active monitoring generates test traffic.

Examples:

```bash
ping example.com
```

```bash
curl -I https://example.com
```

```bash
traceroute example.com
```

Active monitoring answers questions such as:

* Is the service reachable?
* Is the port responding?
* Is HTTP working?
* How long does communication take?

---

# 21. Passive Monitoring

Passive monitoring observes existing traffic rather than generating test traffic.

Example:

```bash
sudo tcpdump
```

Other examples include:

* VPC Flow Logs
* Network device telemetry
* Firewall logs
* Existing traffic statistics

---

# 22. SNMP

SNMP stands for **Simple Network Management Protocol**.

It is commonly used to monitor network devices such as:

* Routers
* Switches
* Firewalls
* Network appliances

SNMP can provide information about:

* Interface traffic
* Errors
* Device health
* CPU
* Memory

---

# 23. ICMP Monitoring

ICMP is commonly used for network diagnostics.

The most familiar example is:

```bash
ping example.com
```

It can help measure:

* Reachability
* Round-trip time
* Packet loss

Important:

A failed ping does not always mean the service is down because ICMP may be blocked.

---

# 24. TCP Monitoring

TCP monitoring can test whether a TCP port is reachable.

Example:

```bash
nc -vz example.com 443
```

This checks whether TCP port 443 is reachable.

TCP monitoring is useful for:

* SSH
* HTTP
* HTTPS
* Databases
* Custom services

---

# 25. HTTP/HTTPS Monitoring

HTTP monitoring checks application-level availability.

Example:

```bash
curl -I https://example.com
```

You can inspect:

* HTTP status code
* Response headers
* Response time
* TLS connection
* Redirects

For example:

```text
200 → successful
301 → redirect
404 → resource not found
500 → server error
503 → service unavailable
```

---

# 26. DNS Monitoring

DNS is critical because applications often depend on name resolution.

Test DNS with:

```bash
dig example.com
```

Check:

* DNS response
* Query time
* Returned IP address
* DNS server
* Record type

DNS problems can appear as application connectivity problems.

---

# 27. Port Monitoring

Port monitoring checks whether a service is listening.

Example:

```bash
ss -lntp
```

Example output may show:

```text
LISTEN
0.0.0.0:22
0.0.0.0:80
0.0.0.0:443
```

Monitoring ports helps detect:

* Service failures
* Unexpected services
* Configuration changes
* Security risks

---

# 28. Service Monitoring

A service can be monitored at multiple levels.

```text
Process
   ↓
Port
   ↓
Protocol
   ↓
Application
```

For example, monitoring an HTTP server:

```text
Process → running
Port → 80 open
HTTP → responding
Application → healthy
```

# 30. `/proc` and `/sys` Network Metrics

Linux exposes kernel and system information through virtual filesystems.

Examples:

```bash
/proc/net/
/sys/class/net/
```

These can contain information about:

* Network interfaces
* Protocol statistics
* Kernel network state

For example:

```bash
cat /proc/net/dev
```

can display interface traffic statistics.


Show interface statistics:


Show interfaces:


# 32. `ss` Command

`ss` displays socket and connection information.

Show all TCP connections:

```bash
ss -ant
```

Show listening TCP ports:

```bash
ss -lnt
```

Show processes:

```bash
ss -lntp
```

Show summary:

```bash
ss -s
```

---

# 33. `ping`

`ping` tests IP connectivity using ICMP echo requests.

Example:

```bash
ping -c 4 8.8.8.8
```

It can show:

* Packets transmitted
* Packets received
* Packet loss
* Round-trip time

---

# 34. `traceroute` and `tracepath`

These tools help identify the network path to a destination.

Example:

```bash
traceroute example.com
```

or:

```bash
tracepath example.com
```

They are useful when investigating:

* Routing problems
* High latency
* Unexpected network paths

---

# 35. `tcpdump`

`tcpdump` captures packets from network interfaces.

Basic command:

```bash
sudo tcpdump
```

Capture a specific interface:

```bash
sudo tcpdump -i eth0
```

Capture traffic for a port:

```bash
sudo tcpdump -i any port 80
```

Save a capture:

```bash
sudo tcpdump -i any -w capture.pcap
```

Packet captures can be analyzed later.

---

# 36. `curl` Health Checks

`curl` is useful for application-level monitoring.

Example:

```bash
curl -I https://example.com
```

Verbose mode:

```bash
curl -v https://example.com
```

Measure timing:

```bash
curl -o /dev/null -s -w 'HTTP=%{http_code} TIME=%{time_total}\n' https://example.com
```

This can be used in health-check scripts.

# 37. Prometheus

Prometheus is an open-source monitoring and alerting system.

Architecture:

```text
Targets
   ↓
Exporters
   ↓
Prometheus
   ↓
PromQL
   ↓
Grafana
```

Prometheus generally uses a **pull-based scrape model**.

It periodically requests metrics from targets.

---

# 38. Prometheus Exporters

An exporter exposes metrics in a format Prometheus can scrape.

Examples:

* Node Exporter
* Blackbox Exporter
* Application exporters

Node Exporter is commonly used for Linux system metrics.

Blackbox Exporter can perform external probes such as HTTP, TCP, DNS, or ICMP-style checks depending on configuration.

---

# 39. Prometheus Scrape Model

Prometheus periodically scrapes targets.

Example:

```text
Prometheus
    |
    | HTTP scrape
    ↓
Target
    |
    ↓
/metrics
```

The target exposes metrics, and Prometheus stores them as time-series data.

---

# 40. Prometheus Metric Types

Prometheus commonly supports four metric types:

### Counter

A value that normally increases.

Example:

```text
HTTP requests
```

### Gauge

A value that can increase or decrease.

Example:

```text
CPU temperature
```

### Histogram

Measures observations in buckets.

Useful for:

```text
Request latency
Request duration
```

### Summary

Calculates observations and quantiles on the client side.

---

# 41. PromQL

PromQL is the query language used by Prometheus.

Example:

```promql
up
```

Another example:

```promql
rate(http_requests_total[5m])
```

PromQL can help answer:

* How many requests are occurring?
* Are targets up?
* What is the error rate?
* How is latency changing?

Example:

```text

     Alert
```

* Actionable

* Reliable

# 46. Alert Fatigue

Alert fatigue occurs when engineers receive too many alerts.

Example:

```text
100 alerts/day
      ↓
Many are irrelevant
      ↓
Engineer starts ignoring alerts
```

This is dangerous.

Better approach:

```text
Fewer
+
Actionable
+
High-quality
alerts
```

# 67. Common Failure Patterns

## High Latency

Possible causes:

* Congestion
* Long routing path
* Server overload
* DNS delay

## Packet Loss

Possible causes:

* Congestion
* Interface errors
* Network failures
* Firewall behavior

## Connection Refused

Usually means the destination was reached but no service accepted the connection on that port, or an active reject occurred.

Check:

```bash
ss -lntp
```

## Connection Timeout

Possible causes:

* Firewall
* Security Group
* Network ACL
* Routing
* Service unreachable

## DNS Failure

Possible causes:

* Resolver failure
* Incorrect DNS configuration
* Network issue
* DNS server unavailable

# 68. Monitoring Best Practices

Follow these principles:

### 1. Monitor what matters

Do not collect data simply because you can.

### 2. Establish baselines

Know what normal looks like.

### 3. Create actionable alerts

Every alert should lead to an action.

### 4. Avoid alert fatigue

Too many alerts reduce their value.

### 5. Monitor dependencies

Applications depend on:

```text
DNS
Network
Database
Storage
External APIs
```

### 6. Monitor from multiple perspectives

Use:

* Infrastructure metrics
* Application metrics
* Logs
* Traces
* Synthetic checks

### 7. Test your alerts

An alert that has never been tested may fail during an incident.


```text

    ↓
```

```text

Check packet loss
      ↓
Check network traffic
      ↓
Check connections
      ↓
```

Possible result:

```text

      ↓

      ↓
```

```text

+
Verify metrics
```
